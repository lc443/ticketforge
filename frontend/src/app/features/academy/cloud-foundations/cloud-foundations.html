Before the AWS names

The cloud means renting technology over the internet

TicketForge needs computers to run the application and places to store information. Instead of buying and maintaining all of that equipment, it can rent services from AWS. A Region is the broad geographic area you choose. An Availability Zone is an isolated location inside that Region, so one location can fail without automatically stopping every location.

The requirement

One facility failure must not stop ticket sales.

Running three API instances in one AZ increases instance redundancy but leaves one shared facility failure domain.

The architecture response

Distribute healthy capacity across AZs.

A regional load balancer routes to capacity in multiple AZs; data services need their own Multi-AZ and recovery decisions.

Exercise 1 · cloud value

Separate scalability, elasticity, and high availability

Scalability    → capacity can grow to handle greater demand
Elasticity     → capacity expands and contracts with demand
High availability → service remains usable through expected failures
Fault tolerance   → service continues with little or no interruption
scalability

Answers whether the design can grow; vertical and horizontal approaches have different ceilings.

elasticity

Adds time and automation: resources track changing demand rather than remaining permanently sized for peak.

availability

Depends on eliminating critical single failure domains, not merely adding more instances.

Exercise 2 · geography

Trace Region, Availability Zone, and edge boundaries

AWS global infrastructure
├── Region: geographic service boundary
│   ├── Availability Zone A: isolated facilities
│   ├── Availability Zone B: isolated facilities
│   └── Availability Zone C: isolated facilities
└── Edge location: selected services closer to users
Region

Drives latency, service availability, legal/data-residency choices, price, and disaster-recovery design.

Availability Zone

An isolated regional failure domain connected to other AZs with low-latency networking.

edge

Supports services such as content delivery and DNS; it is not a synonym for an AZ or a full application Region.

Exercise 3 · account observation

Inspect Regions without creating a resource

aws sts get-caller-identity \
  --profile ticketforge-lab

aws ec2 describe-regions \
  --profile ticketforge-lab \
  --query 'Regions[].RegionName' \
  --output table
preflight first

Identity evidence precedes every AWS command so you know which account receives the action.

--query

Uses a JMESPath expression to select Region names from the larger API response.

read-only

This observation creates no EC2 instance; an API call to the EC2 service is not the same as provisioning compute.

Exercise 4 · shared responsibility

Assign responsibility by service model

AWS responsibility      → security OF the cloud
Customer responsibility → security IN the cloud

EC2: customer manages more OS and workload controls
RDS: AWS manages more database infrastructure operations
S3: customer still owns data classification, access, and configuration
shared

The boundary changes by service; moving to a managed service changes responsibilities rather than eliminating them.

AWS

Protects physical facilities, hardware, and underlying cloud infrastructure.

customer

Still owns identities, data, access choices, workload configuration, and other controls defined by the service.

Exercise 5 · architecture defense

Explain a resilient TicketForge placement

Users
  ↓
Regional load balancer
  ├── AZ A → TicketForge API replicas
  └── AZ B → TicketForge API replicas
              ↓
       Multi-AZ data design

Open questions: Region, RTO, RPO, latency, cost, data residency
multi-AZ

Addresses an AZ-scale failure inside one Region; it is not automatically a multi-Region disaster-recovery plan.

RTO / RPO

Define acceptable recovery time and data loss so resilience decisions can be measured.

tradeoff

Additional failure-domain independence improves resilience but adds cost and operational decisions.
