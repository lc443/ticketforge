Sprint 17 · in progress

CI/CD & software supply chain

Build an automated path from untrusted source change to tested, traceable, promotable container artifact.

The problem

A change can compile locally and still be unsafe to release.

It may use the wrong Java or Node version, break an integration, fail a clean Docker build, contain a vulnerable dependency, or produce an artifact nobody can trace back to reviewed source.

The solution

Make evidence an automated promotion requirement.

Pull requests receive read-only correctness gates. Trusted main builds publish immutable images, scan them, attest their provenance, and promote the same digest between environments.

Build once, promote many

If staging and production rebuild the same Git commit independently, dependency or base-image changes can produce different bytes. TicketForge promotes one verified digest so the artifact tested in staging is exactly the artifact deployed later.

Workflow anatomy

Read GitHub Actions YAML from the outside in

name: Pull request quality gates

on:
  pull_request:
    branches: [main]
  push:
    branches: [main, 'sprint-*']
  workflow_dispatch:

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
name

The human-readable workflow name displayed in the Actions UI and branch-protection check list.

on

Declares events that create a workflow run. YAML treats it as a mapping here, not a shell command.

pull_request

Validates the proposed merge result targeting main. Pull-request code is an untrusted input.

push

Runs after commits reach main or a sprint branch, catching changes made without a pull request.

'sprint-*'

A quoted branch glob. Quoting prevents YAML from interpreting special characters unexpectedly.

workflow_dispatch

Adds a manual Run workflow button for diagnostics. It does not bypass job gates.

concurrency.group

Builds a key from workflow and Git ref. Runs for different branches remain independent.

${{ ... }}

GitHub expression syntax evaluated by Actions before the shell runs. It is different from shell $VARIABLE expansion.

cancel-in-progress

Cancels an older run when a newer commit arrives on the same ref, reducing cost and obsolete feedback.

permissions

Applies least privilege to the generated GITHUB_TOKEN. CI can read source but cannot publish packages.

Job syntax

A job is an isolated runner responsibility

jobs:
  backend:
    name: Backend · Java 21 tests
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - name: Check out the candidate commit
        uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
      - name: Run a command
        run: docker version
jobs

Contains independently scheduled units. Jobs run in parallel unless needs creates a dependency.

backend

A stable internal job identifier used by branch protection, expressions, and downstream needs.

runs-on

Selects the runner operating system. TicketForge needs Linux because Docker networking and service containers are part of the evidence.

timeout-minutes

Bounds cost and prevents a hung dependency or test from consuming a runner indefinitely.

steps

An ordered list sharing the job workspace. A failing step stops later normal steps.

uses

Executes a reusable action. TicketForge pins checkout to a full immutable commit SHA rather than a mutable tag.

run

Executes shell commands on the runner. Multi-line folded YAML with >- becomes one command line.

Backend gate · implemented

Test inside the real dependency network

docker compose -p ticketforge-ci \
  -f infrastructure/docker/docker-compose.yml \
  -f infrastructure/docker/docker-compose.ci.yml \
  up -d --wait postgres redis kafka

docker run --rm \
  --network ticketforge-ci_default \
  -e DB_URL=jdbc:postgresql://postgres:5432/ticketforge \
  -e DB_USERNAME=postgres \
  -e DB_PASSWORD=postgres \
  -e REDIS_HOST=redis \
  -e REDIS_PORT=6379 \
  -e KAFKA_BOOTSTRAP_SERVERS=kafka:9092 \
  -v "$PWD/backend:/workspace" \
  -w /workspace \
  eclipse-temurin:21-jdk \
  ./mvnw -B test
docker compose

Creates the dependency containers and a shared network from the checked-in topology.

-p ticketforge-ci

Sets a deterministic Compose project name. The default network therefore becomes ticketforge-ci_default.

-f

Applies files from left to right. The base defines the topology; the CI override removes fixed host ports and container names so concurrent runners cannot collide.

up -d

Reconciles and starts dependencies in detached mode so the next command can run.

--wait

Waits until selected services are running or healthy instead of relying on startup order.

docker run --rm

Creates a disposable Java test container and removes it after the Maven process exits.

--network

Joins the same DNS domain as the dependencies. This makes Kafka's advertised kafka:9092 address resolvable.

-e

Sets environment variables for Spring configuration. Service names are Compose DNS records, not hostnames on the public internet.

-v

Bind-mounts the checked-out backend into the test container. The left side is runner storage; the right side is container storage.

-w

Sets the container working directory so ./mvnw resolves correctly.

-B

Runs Maven in batch mode: stable, non-interactive output designed for automation.

Failure discovered while building the gate

The first version used host networking. Tests passed, but Kafka advertised kafka:9092 and consumers logged UnknownHostException. Joining the Compose network aligned bootstrap and advertised addresses. A green test alone was weaker evidence than a green test with healthy integration logs.

Failure evidence and cleanup

Diagnostics must run even when the normal path stops

- name: Capture dependency logs after a failure
  if: failure()
  run: docker compose -p ticketforge-ci \
    -f infrastructure/docker/docker-compose.yml \
    -f infrastructure/docker/docker-compose.ci.yml \
    logs --tail=200 postgres redis kafka

- name: Remove integration dependencies
  if: always()
  run: docker compose -p ticketforge-ci \
    -f infrastructure/docker/docker-compose.yml \
    -f infrastructure/docker/docker-compose.ci.yml \
    down --volumes
if: failure()

Runs only after an earlier failure, preserving bounded diagnostic logs without flooding successful runs.

logs --tail=200

Captures the latest 200 lines per dependency. The bound protects log storage and reduces accidental secret exposure.

if: always()

Runs on success, failure, or cancellation. Cleanup cannot depend on the happy path.

down --volumes

Removes the ephemeral CI containers, network, and test data. Never run this against a production Compose project.

Frontend gate · implemented

Use the declared Node runtime and lockfile

docker run --rm \
  -v "$PWD/frontend:/workspace" \
  -w /workspace \
  node:22-alpine \
  sh -c 'npm ci && npm run build'
node:22-alpine

Matches the frontend Docker builder instead of inheriting whichever Node version a runner happens to provide.

sh -c

Starts a shell inside the container so two commands can execute as one controlled script.

npm ci

Installs exactly the lockfile and fails when package metadata disagrees with it. It is the automation form of npm installation.

&&

Runs the build only when installation exits successfully. The right side is skipped after a non-zero exit.

npm run build

Executes Angular's production build, including template checking, TypeScript compilation, bundling, and configured budgets.

Security gates · implemented and verified

Separate correctness from known-risk policy

Dependency review

Compare the pull request's dependency graph with its base and reject newly introduced packages above the agreed severity or license policy.

Container scan

Scan the final API, gateway, and frontend images—not only source manifests—because base operating-system packages also create vulnerabilities.

Report retention

Upload SARIF or another machine-readable report so findings remain searchable and tied to the candidate commit.

Exception governance

A finding may require a time-bounded exception with owner, justification, compensating control, and expiration—not an undocumented skip. 

docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v trivy-cache:/root/.cache/trivy \
  aquasec/trivy:0.58.2 image \
  --scanners vuln \
  --ignore-unfixed \
  --severity HIGH,CRITICAL \
  --exit-code 1 \
  ticketforge-api:${{ github.sha }}
The gate found real defects

The first scan found 35 frontend findings, a vulnerable PostgreSQL JDBC driver, and an unrelated vulnerable Pebble binary in the API runtime. We upgraded pgJDBC, moved the API to a smaller Alpine JRE, patched NGINX packages, and created a scanned gateway artifact instead of weakening the threshold.

GHCR publication · implemented, main-run pending

Write authority exists only after trusted gates

permissions:
  contents: read
  packages: write
  attestations: write
  id-token: write

registry: ghcr.io
username: ${{ github.actor }}
password: ${{ secrets.GITHUB_TOKEN }}
docker save --output ticketforge-images.tar \
  ticketforge-api:${{ github.sha }} \
  ticketforge-gateway:${{ github.sha }} \
  ticketforge-frontend:${{ github.sha }}

docker load --input ticketforge-images.tar

docker tag ticketforge-api:${{ github.sha }} \
  ghcr.io/${{ github.repository_owner }}/ticketforge-api:sha-${{ github.sha }}

docker push \
  ghcr.io/${{ github.repository_owner }}/ticketforge-api:sha-${{ github.sha }}
packages: write

Allows the trusted job to push GHCR packages. It must not be a workflow-wide pull-request permission.

attestations: write

Allows GitHub to store provenance statements associated with the artifact.

id-token: write

Allows short-lived OIDC identity issuance. It does not expose a permanent cloud key by itself.

github.actor

The identity that triggered the trusted workflow and is used as the GHCR login username.

secrets.GITHUB_TOKEN

An automatically generated, repository-scoped credential whose permissions are constrained by the job declaration.

docker save / docker load

Transfers the exact locally scanned image between isolated jobs. The publication job does not rebuild and accidentally create different bytes.

docker tag / docker push

Adds the registry-qualified immutable commit tag, then uploads that already-verified image to GHCR. The workflow repeats this operation for all three artifacts. 

- name: Attest the API image provenance
  uses: actions/attest@c32b4b8b198b65d0bd9d63490e847ff7b53989d4
  with:
    subject-name: ghcr.io/${{ github.repository_owner }}/ticketforge-api
    subject-digest: ${{ steps.push.outputs.api-digest }}
    push-to-registry: true

The attestation names the registry package and binds it to the digest returned after push. Consumers can therefore verify which repository, commit, and trusted workflow produced the deployed bytes.

Artifact identity · implemented, registry proof pending

Tags help humans; digests identify bytes

ghcr.io/lc443/ticketforge-api:sha-e180ac8
ghcr.io/lc443/ticketforge-api@sha256:<immutable-digest>
registry/owner/image

The globally qualified package name. TicketForge publishes API, gateway, and frontend as separate deployable artifacts.

:sha-…

A readable tag linked to source revision. Registry tags can still be moved and are not the final integrity guarantee.

@sha256:…

A content digest computed from the image manifest. Changing artifact bytes changes the digest.

provenance

A signed statement connecting digest, source repository, commit, workflow, and build identity so consumers can verify origin.

Promotion and rollback · implemented and verified

Deployment changes a reference, not source code

export API_IMAGE='ghcr.io/lc443/ticketforge-api@sha256:<verified-digest>'
export GATEWAY_IMAGE='ghcr.io/lc443/ticketforge-gateway@sha256:<verified-digest>'
export FRONTEND_IMAGE='ghcr.io/lc443/ticketforge-frontend@sha256:<verified-digest>'

docker compose \
  -f infrastructure/docker/docker-compose.yml \
  -f infrastructure/docker/docker-compose.release.yml \
  pull api1 api2 api3 api-gateway frontend

docker compose \
  -f infrastructure/docker/docker-compose.yml \
  -f infrastructure/docker/docker-compose.release.yml \
  up -d --no-build --wait api1 api2 api3 api-gateway frontend
API_IMAGE=…

Shell variable assignment for one command environment. The value is an artifact coordinate, not a build instruction.

build: !reset null

Compose override syntax that removes the base file's build instruction. Release deployment must fail when a digest is absent instead of silently rebuilding locally.

--no-build

Runtime enforcement of the same invariant: pull and start the approved artifact, but do not produce a replacement during deployment.

environment

A GitHub deployment boundary such as staging or production with separate approvals, secrets, and history.

promotion

Authorizes an existing digest for the next environment after evidence and approval; it does not compile again.

rollback

Restores a previously verified digest. Database compatibility and irreversible migrations must be assessed separately.

Architect takeaway

A pipeline is an executable governance model

CI/CD is not only automation syntax. It defines who may produce artifacts, which evidence is mandatory, where secrets exist, how identity is preserved, how environments approve risk, and how the system returns to a known state after failure.
