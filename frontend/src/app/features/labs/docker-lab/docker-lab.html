Sprint 15

Docker & NGINX: build and route TicketForge from scratch

Learn how source becomes immutable images, how Compose creates the runtime topology, and how two NGINX layers route every browser request to a healthy API replica.

The problem

“It runs on my machine” is not a deployment strategy.

Host-built JARs, duplicated replica images, missing health gates, and container-local database files make releases inconsistent and fragile.

The solution

Build immutable images and externalize state.

Multi-stage builds compile in Docker, three APIs share one digest, health checks order startup, and PostgreSQL data lives in a named volume.

Core model

Image ≠ container

ImageRead-only recipe and filesystem. Built once and identified by a digest.
ContainerA running instance of that image with a small writable layer.
VolumeState with a lifecycle independent of a disposable container.
End-to-end mental model

Follow one request before reading configuration

A container port is private until it is published or reached through the Compose network.

Why two NGINX layers?

The frontend NGINX serves Angular and converts same-origin /api requests into internal gateway requests. The gateway NGINX has a different job: distribute those requests across three API containers and retry bounded infrastructure failures.

Build from zero · Part 1

Construct the API image

A multi-stage Dockerfile separates compilation tools from the smaller production runtime.

FROM eclipse-temurin:21-jdk AS build
WORKDIR /workspace

COPY backend/.mvn .mvn
COPY backend/mvnw backend/pom.xml ./
RUN ./mvnw -B dependency:go-offline

COPY backend/src src
RUN ./mvnw -B clean package -DskipTests

FROM eclipse-temurin:21-jre

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/* \
    && groupadd --system ticketforge \
    && useradd --system --gid ticketforge --home-dir /app ticketforge

WORKDIR /app
COPY --from=build --chown=ticketforge:ticketforge /workspace/target/ticketforge-*.jar app.jar
USER ticketforge
EXPOSE 8080
LABEL org.opencontainers.image.title="TicketForge API" \
      org.opencontainers.image.description="TicketForge Spring Boot modular monolith"
ENTRYPOINT ["java", "-jar", "app.jar"]
FROM … AS build

Starts a build stage from a Java 21 JDK. AS build names it so a later stage can copy its artifact.

WORKDIR /workspace

Creates or selects the working directory. Later relative COPY and RUN operations use it.

COPY source destination

Copies files from the build context—not from the Dockerfile’s directory—into the current image layer.

RUN …

Executes during image build time and stores filesystem changes in a new immutable layer.

FROM …:jre

Begins a clean runtime stage. Maven, source code, and the JDK do not automatically cross this boundary.

RUN apt-get …

Installs curl for the health check, removes package indexes to keep the layer smaller, and creates a non-root Linux user and group.

COPY --from=build

Copies only the packaged JAR from the named build stage into the runtime stage.

--chown

Assigns ownership while copying so the non-root runtime user can read the application artifact.

USER ticketforge

Runs later instructions and the container process without root privileges.

EXPOSE 8080

Documents the intended container port. It does not publish that port to your Mac; Compose ports does that.

ENTRYPOINT […]

Defines the runtime process using exec-form JSON, so Java receives signals directly as PID 1.

Build only the API image 
docker compose -f infrastructure/docker/docker-compose.yml build api1

-f selects the Compose file. build api1 follows api1’s build definition and tags the result as ticketforge-api:local.

Build from zero · Part 2

Construct the frontend image

Angular is compiled with Node, but production runs only static files in NGINX.

FROM node:22-alpine AS build
WORKDIR /workspace
COPY frontend/package.json frontend/package-lock.json frontend/.npmrc ./
RUN npm ci
COPY frontend/ ./
RUN npm run build

FROM nginx:1.27-alpine
COPY infrastructure/nginx/frontend.conf /etc/nginx/conf.d/default.conf
COPY --from=build /workspace/dist/ticketforge/browser /usr/share/nginx/html
EXPOSE 80
HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=5 \
  CMD wget -qO- http://127.0.0.1/health || exit 1
npm ci

Installs exactly what the lockfile records. Copying dependency metadata first allows this expensive layer to remain cached when only source changes.

COPY frontend/ ./

Copies application source only after dependencies, preserving Docker’s cache boundary.

FROM nginx…

Starts a new production stage. Node and node_modules are absent from the final image.

/usr/share/nginx/html

Is the directory from which the NGINX image serves static Angular assets.

HEALTHCHECK

Runs inside the container every ten seconds. After a five-second startup grace period, five consecutive failures mark it unhealthy.

Build from zero · Part 3

Compose the runtime system

Compose describes containers, their configuration, their dependencies, and shared resources.

x-api-runtime: &api-runtime
  image: ticketforge-api:local
  environment:
    DB_URL: jdbc:postgresql://postgres:5432/ticketforge
  depends_on:
    postgres:
      condition: service_healthy

services:
  api1:
    <<: *api-runtime
    build:
      context: ../..
      dockerfile: infrastructure/docker/Dockerfile.api
    ports:
      - "8081:8080"

  api2:
    <<: *api-runtime
    ports:
      - "8082:8080"

volumes:
  postgres-data:
    name: ticketforge-postgres-data
x-api-runtime

An extension field ignored as a service. It stores reusable YAML configuration.

&api-runtime

Creates a YAML anchor; <<: *api-runtime merges that configuration into each API replica.

image

All replicas reference the same tagged artifact. Only api1 declares build, preventing three duplicate builds.

postgres:5432

postgres is Compose service DNS and 5432 is the container port. Containers do not use the host’s localhost:5432 to reach each other.

condition: service_healthy

Waits for the dependency health check. Plain startup order cannot prove PostgreSQL is ready to accept connections.

"8081:8080"

Maps host port 8081 to container port 8080. Traffic inside the Compose network still targets api1:8080.

postgres-data

A named volume outlives replacement of the PostgreSQL container and preserves durable database files.

Build from zero · Part 4

Configure the API gateway NGINX

NGINX configuration is hierarchical: directives are valid only in specific contexts.

events {}

http {
  upstream ticketforge_api {
    server api1:8080 max_fails=1 fail_timeout=10s;
    server api2:8080 max_fails=1 fail_timeout=10s;
    server api3:8080 max_fails=1 fail_timeout=10s;
  }

  server {
    listen 80;

    location / {
      proxy_pass http://ticketforge_api;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
      proxy_connect_timeout 1s;
      proxy_next_upstream error timeout http_502 http_503 http_504;
      proxy_next_upstream_tries 3;
    }
  }
}
events {}

Required top-level NGINX context for connection-processing configuration. TicketForge accepts its defaults.

http {…}

Contains HTTP-wide configuration, upstream pools, virtual servers, and locations.

upstream

Names a backend pool. With no alternate method configured, NGINX distributes requests round-robin.

max_fails / fail_timeout

Marks a peer unavailable after the configured failures for a bounded period; this is passive health detection.

server / listen

Defines a virtual HTTP server listening on container port 80.

location /

A prefix match that handles every URI not claimed by a more-specific location.

proxy_pass

Forwards the original URI to the named upstream because no replacement URI follows the upstream name.

X-Forwarded-For

Appends the client address to the proxy chain instead of losing origin information at each hop.

proxy_next_upstream

Retries only the listed infrastructure failures. Application responses such as 400, 401, 403, or 409 remain authoritative.

Build from zero · Part 5

Serve Angular and proxy same-origin API calls

The frontend NGINX chooses between health, API proxying, real static files, and Angular routing.

server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  location = /health {
    return 200 "healthy\n";
  }

  location /api/ {
    proxy_pass http://api-gateway;
  }

  location / {
    try_files $uri $uri/ /index.html;
  }
}
location = /health

The = makes this an exact match, so only that URI returns the container health response.

location /api/

This longer prefix wins over location /. Because proxy_pass has no trailing replacement path, NGINX preserves /api/….

try_files

Serves an existing asset first. If no file exists, it returns index.html so Angular can resolve routes such as /roadmap.

api-gateway

Compose DNS resolves this service name on the private network; it is not a public Internet hostname.

Validate before startup

Catch configuration errors early

docker compose -f infrastructure/docker/docker-compose.yml config
docker compose -f infrastructure/docker/docker-compose.yml build
docker run --rm -v "$PWD/infrastructure/nginx/nginx.conf:/etc/nginx/nginx.conf:ro" nginx:1.27-alpine nginx -t

config resolves YAML anchors and environment interpolation. build proves both Dockerfiles. nginx -t parses the gateway configuration without starting the full system; --rm removes this temporary validation container afterward.

Production loop

Build, start, observe

docker compose -f infrastructure/docker/docker-compose.yml up -d --build
docker compose -f infrastructure/docker/docker-compose.yml ps
docker compose -f infrastructure/docker/docker-compose.yml logs -f --tail=200 api1 api2 api3

up creates or recreates the declared system, -d detaches from its output, and --build rebuilds images before startup. ps reports lifecycle and health; logs -f follows output; --tail=200 limits the initial history.

Diagnose the failure path

Inspect rather than guess

docker compose -f infrastructure/docker/docker-compose.yml ps
docker compose -f infrastructure/docker/docker-compose.yml logs --tail=200 api-gateway api1
docker compose -f infrastructure/docker/docker-compose.yml exec api-gateway nginx -t
docker compose -f infrastructure/docker/docker-compose.yml exec api-gateway wget -qO- http://api1:8080/actuator/health
curl -i http://localhost:4200/api/events

Read this sequence from outside inward: container health, proxy/application logs, loaded NGINX syntax, private-network reachability, then the complete public request path.

From-scratch exercise

Rebuild the topology without copying it

  1. Write a two-stage API Dockerfile that leaves Maven and the JDK out of production.
  2. Write a two-stage frontend Dockerfile that serves only compiled Angular files.
  3. Define PostgreSQL with a named volume and a readiness health check.
  4. Create three API services from one image and give each a different host port.
  5. Write an NGINX upstream and prove requests reach more than one replica.
  6. Stop one replica, repeat requests, and explain the first-failure latency.
  7. Recreate PostgreSQL and prove the data survived independently of its container.
