Distributed Locking Lab

Two API instances. Each one thinks it's the only one holding the lock.

TicketForge still runs Sprint 7's pessimistic lock straight against PostgreSQL — that part is safe regardless of how many API instances call it, because the lock lives in the database, not in any one JVM. This lab is about the case that isn't covered: a critical section that isn't a single database transaction.

The problem

A local lock only knows about its own process.

API #1                     API #2
   │                          │
synchronized(ticket)   synchronized(ticket)
   │                          │
   └─────────────┬────────────┘
                 ▼
            PostgreSQL

Each JVM has its own lock — a local `synchronized`
block only coordinates threads inside ONE process.
The solution

A lock every instance actually shares.

A distributed lock (Redis SET NX + TTL, or similar) lives outside any single JVM. Every instance checks the same lock before entering the critical section — not just the threads inside its own process.

Open question — README leaves this to you

When should you NOT use a distributed lock? In Feb 2016, Martin Kleppmann publicly argued Redis's own Redlock algorithm is unsafe under clock drift and process pauses, lacking fencing tokens. Redis's creator, antirez, wrote a public rebuttal defending it. Two serious engineers, same algorithm, different conclusions — read both before deciding.
