Distributed Locking Lab

The best distributed lock is the one that protects the data in the system where it already lives.

A Java synchronized lock belongs to one JVM. TicketForge has three JVMs, so local locks cannot protect shared inventory. PostgreSQL is shared by every replica and owns the inventory transaction, making its row lock a distributed coordination mechanism.

The problem

Local memory stops at the process boundary.

TicketForge's solution

Lock the PostgreSQL row being changed.

SELECT … FOR UPDATE makes competing transactions wait. The loser re-reads committed inventory before deciding.

Architecture decision

Do not add Redis by default. A Redis lease would coordinate replicas, but it would split the lock and transaction across two failure domains. PostgreSQL already provides the required guarantee atomically.
