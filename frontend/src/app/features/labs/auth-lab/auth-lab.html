Authentication & Authorization Lab

Log in, inspect the token, then try to break it.

The problem

Sessions don't scale horizontally for free.

A server-side session lives in one instance's memory. Sprint 4 puts N API instances behind a load balancer — the instance that handles request #2 might not be the one that handled the login.

The solution

A signed token the client carries.

Login returns a JWT. Every later request sends it in the Authorization header. Any instance can verify the signature and read the role — no shared session store required.

Why it works
  • Stateless. No server-side session to keep in sync across instances.
  • Self-contained. Role and identity travel with the token.
  • Signature-verified. The client can read a token but can't forge one.
The problem

Every protected call 401'd — even with a valid token.

JwtAuthenticationFilter checked the signature and let the request through, but never told Spring Security who the request was. With no Authentication in the SecurityContext, anyRequest().authenticated() rejected it anyway.

The solution

Set the SecurityContext after validating.

On a valid token, extract the email from the subject claim and call SecurityContextHolder.getContext().setAuthentication(...) before the filter chain continues.

Why it works
  • Authentication answers "is this token genuine and unexpired" — validateToken() alone.
  • Authorization is a separate downstream check — Spring's filter chain reads the SecurityContext, not the raw header.
  • Skipping the second step is a common real bug: the filter runs, nothing throws, and the request still 401s.

401 versus 403

401 means authentication is absent or invalid. 403 means identity is established but policy denies the requested action.

Trust boundary

JWT payloads are encoded, not secret. Never trust claims until signature, algorithm, expiry, and expected issuer/audience rules have been validated.

  1. Hash stored passwords with an adaptive password encoder.
  2. Issue the smallest useful set of claims.
  3. Validate the token before populating the security context.
  4. Test missing, malformed, expired, tampered, and insufficient-permission cases.
