Requirements & Architecture Lab

No code in this sprint. Just the document that everything else has to trace back to.

The problem

"Build a ticketing app" isn't a spec.

Availability, latency, RPO/RTO, who can do what — none of it is obvious from a feature list. Skip this step and every later decision (locking strategy, cache TTL, AWS instance size) is a guess with nothing to check it against.

The solution

Requirements doc, diagrams, and an ADR — before line one.

Functional requirements, non-functional targets, a system context diagram, and ADR-001 justifying the modular monolith. Every sprint after this one is allowed to reference it.

Why it works
  • Traceability. "Why Redis?" has an answer that isn't "because it's popular."
  • Forces numbers. "Fast" becomes "p95 < 500ms" — testable, not vibes.
  • Shared context. An ADR lets someone new understand a decision without asking you.
Reference

ADR template

The shape every architecture decision in this project follows.

ADR-XXX: <Decision Title>

Context:       Why is a decision needed here?
Decision:      What are we doing?
Alternatives:  What else did we consider?
Consequences:  What does this make easier or harder?
Tradeoffs:     What are we giving up?

Quality scenario

Replace “the system is fast” with source, stimulus, environment, response, and measure—for example, authenticated event reads remain below a defined p95 under a defined request rate.

Traceability

Connect each material decision to a requirement and each requirement to a test, drill, metric, or review that can prove it.

  1. Interview for goals, actors, constraints, and failure impact.
  2. Separate functional behavior from measurable quality attributes.
  3. Draw the system boundary and external dependencies.
  4. Record one consequential decision with alternatives and consequences.
