Concurrency & Overselling Lab

One ticket left. Two buyers click at the same instant. Toggle the lock and see.

The problem

Read, then write — with a gap in between.

Customer A: read tickets = 1
Customer B: read tickets = 1
Customer A: write tickets = 0   ✓ sold
Customer B: write tickets = 0   ✓ sold

Tickets sold: 2      ← oversold
The solution

Pessimistic locking — SELECT ... FOR UPDATE.

Customer A: locks the row, reads 1, writes 0, commits
Customer B: blocked until A commits
Customer B: reads 0   ← sold out, rejected

Tickets sold: 1
Why it works
  • Atomicity. The read and the write happen as one uninterruptible unit.
  • Serialized access. The second transaction can't act on stale data.
  • Tradeoff. Contention forces waiting — fine for one row, not free at scale.

Race window

The vulnerable sequence is check-then-act: both transactions can observe the same old value unless access is serialized or the write is made conditional.

Alternative

An atomic conditional update can avoid blocking locks, but it changes how conflicts and returned state are modeled. Choose with measured contention in mind.

  1. Write the invariant mathematically.
  2. Create deterministic contention around the same record.
  3. Assert winner count, loser contract, and durable final state.
  4. Repeat through all replicas rather than one JVM.
