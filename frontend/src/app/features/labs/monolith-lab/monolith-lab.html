Modular Monolith Lab

Same "Reserve Ticket" flow, two ways to wire it. Watch what changes.

The problem

Microservices from day one, for 5 users.

Every module call becomes a network call. Every network call can fail on its own, independent of the others. A feature that used to be one transaction is now four services that have to agree.

The solution

One deployable, clean module boundaries.

auth, event, inventory, reservation, order — separate packages, one JVM. Calls are method calls, not network calls. Split a module out later, once it's actually earned it.

Why it works
  • No partial failure. One process, one transaction, one outcome.
  • No network latency between modules that talk constantly.
  • Simple to deploy and debug — one artifact, one log stream.

One deployable

The packaged JAR contains every module. Method calls replace network calls, and one database transaction can preserve reservation invariants.

Extraction signal

Consider a service boundary only when independent scaling, ownership, release cadence, data isolation, or fault isolation outweigh distributed-system cost.

  1. Name capabilities rather than technical layers.
  2. Give each capability controllers, services, repositories, and models.
  3. Make cross-module dependencies explicit.
  4. Document what evidence would justify extracting one module later.
