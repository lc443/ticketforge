Sprint 21

Kubernetes autoscaling

Turn resource telemetry into bounded capacity decisions, then prove scale-out, stabilization, and recovery.

The problem

Fixed capacity is either late or wasteful.

Too few replicas miss latency goals; permanent peak replicas waste compute. Scaling without node headroom can collapse the platform.

The solution

Scale from measured demand inside safety bounds.

Metrics Server supplies resource observations; HPA compares usage to requests; behavior policies control speed; min/max replicas cap availability and cost.

Exercise 2 · scaling math

Understand the denominator

utilization = current CPU ÷ requested CPU × 100

25m ÷ 500m × 100 = 5%
400m ÷ 500m × 100 = 80%

desired replicas ≈ current replicas × current utilization ÷ target
3 × 80 ÷ 70 = 3.43 → 4 replicas
requests.cpu

Scheduling reservation and utilization denominator. An inaccurate request produces an inaccurate scaling signal.

limits.cpu

Maximum CPU consumption before throttling; it is not the HPA denominator.

round up

Capacity must meet demand, so fractional desired replicas become the next whole Pod.

Exercise 3 · bounded policy

Declare target, floor, ceiling, and behavior

minReplicas: 3
maxReplicas: 4
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
  scaleDown:
    stabilizationWindowSeconds: 120
metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
minReplicas

Availability/cold-start floor even when demand is low.

maxReplicas

Cost and cluster-capacity circuit breaker.

stabilizationWindowSeconds

Uses recent recommendations to avoid rapid scale-down oscillation.

Exercise 6 · failure analysis

Recognize when scaling reduces capacity

Observed failed experiment

100m request → 645% reported utilization
HPA 3 → 6 replicas
kind node CPU → approximately 12.5 cores
API, PostgreSQL, scheduler, and control-plane probes failed

Correction

500m measured request · 70% target · max 4 locally
3 → 4 under load · 4 → 3 after demand
HPA

Creates desired Pods; it cannot create node capacity. Cluster Autoscaler is a separate control loop.

background work

Per-replica Kafka consumers, pools, and scheduled work can increase total cost as replicas grow.

capacity model

Connect maximum Pods to node allocatable CPU/memory, dependency connections, and cost before production.
