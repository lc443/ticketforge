Rate Limiting Lab

A 5-token bucket, refilling 1 token every 1.5s. Try to drain it.

The problem

A burst — bot or bug — can hammer one endpoint.

Without a limit, one client can starve every other client of capacity.

The solution

A token bucket in Redis, shared across instances.

Each request costs a token. Tokens refill on a schedule. Empty bucket → 429.

Why it works
  • Bursts allowed, sustained abuse blocked — unlike a hard per-second cap.
  • Shared in Redis — the limit holds even across N load-balanced instances.
  • Atomic increments prevent two simultaneous requests from both slipping through.

Syntax

exec redis runs a command inside the existing Redis service. --scan iterates keys safely; the pattern narrows results to this policy.

Tradeoff

The implementation is a fixed window, not the five-token simulation above. Fixed windows are simple but permit boundary bursts and need an atomic increment/expiry design.

  1. Define the protected resource and client identity.
  2. Choose a limit, window, and rejection contract.
  3. Make state shared across replicas.
  4. Test allowed traffic, exhausted capacity, expiry, and Redis failure behavior.
