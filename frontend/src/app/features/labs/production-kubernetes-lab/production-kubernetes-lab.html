Sprint 19

Production Kubernetes

Protect data, distinguish traffic readiness from process life, drain safely, and make releases reversible.

The problem

Running Pods are not enough.

A process can run while its database is unavailable; a replacement can receive traffic too early; an ephemeral database loses sales records.

The solution

Encode lifecycle and availability policy.

Persistent claims protect Pod replacement, probe groups control traffic, graceful shutdown drains requests, and rollout history provides recovery.

Exercise 1 · persistent state

Prove data survives Pod replacement

A StatefulSet gives PostgreSQL stable identity; its claim lifecycle is separate from the disposable Pod.

kubectl get statefulset,persistentvolumeclaim --namespace ticketforge

kubectl exec --namespace ticketforge postgres-0 -- \
  psql -U postgres -d ticketforge -c \
  "CREATE TABLE IF NOT EXISTS sprint19_canary(id int primary key, note text);"

kubectl delete pod postgres-0 --namespace ticketforge
kubectl rollout status statefulset/postgres --namespace ticketforge

kubectl exec --namespace ticketforge postgres-0 -- \
  psql -U postgres -d ticketforge -c "SELECT * FROM sprint19_canary;"
volumeClaimTemplates

Creates one durable claim per StatefulSet ordinal.

ReadWriteOnce

The volume may be mounted read-write by one node; it does not mean one Pod globally in every storage system.

delete pod

Tests Pod replacement only—not node loss, backups, restore, or regional disaster recovery.

Exercise 2 · health semantics

Ask two different questions

kubectl get --raw \
  /api/v1/namespaces/ticketforge/services/ticketforge-api:8080/proxy/actuator/health/liveness

kubectl get --raw \
  /api/v1/namespaces/ticketforge/services/ticketforge-api:8080/proxy/actuator/health/readiness
liveness

Can this process make progress? Failure restarts the container.

readiness

Can this instance serve requests now? Database or Redis failure removes it from Service endpoints without causing a restart loop.

startup

Suppresses liveness/readiness decisions until slow application initialization completes.

Exercise 3 · graceful termination

Drain before stopping

server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s

terminationGracePeriodSeconds: 35
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 5"]
preStop

Creates a short endpoint-removal window before SIGTERM reaches the app.

25s + 5s < 35s

The container receives enough grace for the hook and Spring request draining before SIGKILL.

Exercise 4 · voluntary disruption

Preserve quorum-like API capacity

kubectl get poddisruptionbudget ticketforge-api \
  --namespace ticketforge

kubectl describe poddisruptionbudget ticketforge-api \
  --namespace ticketforge
minAvailable: 2

With three healthy replicas, one voluntary eviction is allowed.

ALLOWED DISRUPTIONS

The live budget computed by Kubernetes—not a static promise.

PDB

Protects voluntary eviction such as drains, not crashes, direct Pod deletion, or application correctness.

base

Reusable workload identity and common runtime controls.

overlay

Environment-specific image, replicas, labels, and availability policy.

immutable release

Replace the production placeholder with a digest or unique release tag during promotion.

Storage lesson

A StatefulSet claim template is immutable after creation. Expand the bound PVC only when its StorageClass supports expansion, or plan a data migration; do not hide the change in an overlay.

Exercise 6 · release recovery

Observe a rollout and reverse it

kubectl set image deployment/ticketforge-api \
  api=ticketforge-api:<new-release> \
  --namespace ticketforge

kubectl rollout status deployment/ticketforge-api \
  --namespace ticketforge --timeout=240s

kubectl rollout history deployment/ticketforge-api \
  --namespace ticketforge

kubectl rollout undo deployment/ticketforge-api \
  --namespace ticketforge

kubectl rollout status deployment/ticketforge-api \
  --namespace ticketforge --timeout=240s
maxUnavailable

Limits old capacity removed during an update.

maxSurge

Limits temporary extra capacity while new Pods prove readiness.

rollout undo

Restores the previous Pod template; it does not reverse database migrations or external side effects.
