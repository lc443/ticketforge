Sprint 16

Event lifecycle & API evolution

Turn “add edit and delete” into an ownership, data-retention, concurrency, and support design.

The problem

Deleting the row erases business context.

Customers still have reservations, support needs history, and downstream messages may still refer to the event ID.

The solution

Model cancellation as a state transition.

Stop new reservations, preserve committed records, authorize the organizer, and write the audit entry in the same transaction.
Policy

Define the rules before the endpoints

OwnershipThe creating user becomes organizer. Organizer or ADMIN may manage; everyone may read.
InventoryAn edit preserves tickets already sold and cannot reduce capacity below that number.
CancellationSCHEDULED → CANCELLED is valid and repeat requests are idempotent.
DeletionHard delete is allowed only when no reservations exist; otherwise return a structured 409.
ConcurrencyThe client returns the loaded version. A stale write receives 409 instead of overwriting newer data.
AuditCreate, update, cancel, and delete record actor, time, action, and explanation.
HTTP contract

Use verbs that express intent

PUT /api/events/42→replace editable event details
PATCH /api/events/42/status→change one lifecycle field
GET /api/events/42/audit→organizer support evidence
DELETE /api/events/42→only an unreserved event
Why PATCH for cancellation?

The client is changing one part of the resource. A full PUT would require it to resend fields unrelated to the lifecycle decision and increases accidental overwrite risk.

Run the evidence

Build, deploy, and inspect all three replicas

Run focused Java 21 tests
docker run --rm \
  -v "$PWD/backend:/workspace" \
  -w /workspace eclipse-temurin:21-jdk \
  ./mvnw -Dtest=EventServiceTest test

--rm removes the disposable test container. -v mounts backend source and -w selects it as the working directory.

Rebuild and replace the API and frontend containers
docker compose -f infrastructure/docker/docker-compose.yml \
  up -d --build api1 api2 api3 api-gateway frontend

up reconciles desired state, -d runs detached, and --build creates the new shared API image before replacing replicas.

Verify replica health and startup
docker compose -f infrastructure/docker/docker-compose.yml ps
docker compose -f infrastructure/docker/docker-compose.yml logs --tail=100 api1 api2 api3

Healthy containers prove process readiness; logs reveal schema migration or startup failures across every replica.
