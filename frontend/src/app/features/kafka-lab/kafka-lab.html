One ticket left. User hits Reserve. Locking already guarantees only one buyer wins — that part's solved. This is about what happens after the reservation succeeds.

The problem

Everything runs in the same request.

Purchase
  ↓
Save Order       (fast)
  ↓
Send Email       (slow, third-party)
  ↓
Generate Ticket
  ↓
Update Analytics
  ↓
Notify Admin
  ↓
Return Response  (customer still waiting)

The reservation was safe the moment the lock committed — but the response doesn't return until every step below it finishes. A slow email provider makes a successful reservation look like a failed purchase.

The solution

Publish an event, return immediately.

Purchase
  ↓
Save Order + Publish Event   (still fast)
  ↓
Return Response

── off the request thread ──
Kafka: reservation-created
  ├── EmailWorker
  └── AnalyticsWorker

Exactly what ReservationProducer → KafkaConfig → EmailWorker / AnalyticsWorker do today. The request only waits on the DB write and the publish.

Why Kafka solves this

The pattern: event-driven architecture — services react to published events instead of calling each other directly.

  • Decoupling. Reservation no longer depends on email being up.
  • Durability. A published event survives a worker crash.
  • Independent scaling. Scale EmailWorker alone, not the whole API.
  • Failure isolation. Retry + DLQ mean a broken event is delayed, not lost.

Not part of this pipeline: authentication (JWT — who's making the request) and authorization (RBAC — are they allowed to). Both already ran before ReservationService touched this event. Auth guards the request; it has no place inside the event pipeline.

The problem

At-least-once delivery means "at least," not "exactly."

A consumer rebalance, a slow EmailWorker, or a retry after a transient failure can hand the same ReservationCreatedEvent to a worker more than once. Nothing in Kafka — and nothing in EmailWorker or AnalyticsWorker as written — stopped that from sending a second confirmation email or double-counting a sale.

The solution

Claim the event before acting on it.

A new processed_events table with a unique constraint on (consumer_name, event_id). Each worker checks it first, then inserts a claim row before running its side effect. If the insert violates the constraint, the worker lost a race with itself and backs off instead of duplicating the work.

Why insert-first, not check-then-insert
  • Check-then-insert has a race window. Two redeliveries can both pass existsByConsumerNameAndEventId before either has inserted — both would then process the event.
  • The unique constraint is the actual guarantee. The database enforces it atomically; the existence check beforehand is only a cheap fast path to skip most duplicates without paying for a failed insert.
  • Retry/DLQ (Sprint 12) solves a different problem. It guarantees a message isn't lost. It says nothing about a message being delivered twice — that's what idempotency handles.

ddl-auto: update creates processed_events automatically the next time the backend starts — no manual migration needed.

The problem

@Transactional only covers the database.

ReservationService.createReservation() saved the reservation, then called reservationProducer.publish(...) straight to Kafka — inside the same method, but not inside the same transaction. Postgres and Kafka are two separate systems with two separate commit protocols. If the process dies between the DB commit and the Kafka send, the reservation exists but no event ever goes out — no email, no analytics, and nothing retries it, because nothing failed from the database's point of view.

The solution

Write the event as a row, in the same transaction.

ReservationService now writes an OutboxEvent row — the event, already serialized to JSON — inside the exact same @Transactional method as the reservation. A separate OutboxPublisher, on its own schedule, reads unpublished rows and sends them to Kafka afterward.

Why this is the fix, not just a workaround
  • The database is what actually guarantees atomicity here. The reservation row and its outbox row commit together or not at all — that's a normal single-transaction commit, nothing Kafka-specific about it.
  • Publishing becomes a separate, retryable concern. If Kafka is briefly unreachable, the outbox row just sits there unpublished — the reservation itself already succeeded and returned a response.
  • This leans on Sprint 13, not around it. If OutboxPublisher crashes after Kafka acks a send but before marking the row published, the next poll resends it — a duplicate delivery. That's a no-op downstream because EmailWorker/AnalyticsWorker are already idempotent.

outbox_events is created automatically via ddl-auto: update. OutboxPublisher needs @EnableScheduling on the main application class to actually fire — without it, @Scheduled is silently ignored.
